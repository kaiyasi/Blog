### 前言

回想當初水完第三屆 THJCC 的網管組時，我整個人其實處於一種「甚至不知道剛剛到底發生了什麼，比賽就莫名其妙結束了 ww」的狀態。沒想到時隔一年，機緣巧合之下，我這次竟然直接升格，接下了「網管組組長」的重任。

在正式進入正題之前，先來個簡短的自我介紹：我是 Kaiyasi，目前是中興大學應用數學系的大一生，同時也擔任 SCAICT（中南部高中資訊社團聯合）的資訊部長。平時的興趣與學習重心，主要圍繞在全端網頁開發、系統架構規劃，以及資安領域的實務探索。

這次賽事告一段落後，承蒙總召交代給我的賽後任務，決定來寫這篇相當非典型的 "Writeup"。不同於一般解題為主的 Writeup，這篇文章想從維運與架構的角度出發，跟大家聊聊「CTF 網管這個職位到底在忙些什麼？」、「賽前、賽中到賽後會踩到哪些大坑與意外？」，以及我們幕後團隊究竟是如何一步步把整個比賽的網路與基礎設施穩定撐起來的。

### 賽前比賽環境建置

#### 1. 窮學生的救星：感謝國雲網路 (NCSE Network)
老實說，辦過學生競賽或社團活動的人都知道，每次籌備期最讓人頭痛的除了出題跟找贊助之外，就是「伺服器跟機器到底要去哪裡生？」了。如果每個伺服器都要自掏腰包去租公有雲，那窮學生辦完一場比賽大概要直接去路邊吃土。

所以這裡必須先大力感謝 **國雲網路 (NCSE Network, ncse.tw)** 的社群贊助計畫！這次 2026 THJCC 夏季賽能順利把整套環境拉起來，完全是仰賴國雲網路慷慨贊助的高效能 VPS 主機與穩定的頻寬資源。不管是網路連線品質、主機效能還是技術支援，都讓我們在背後架設時安心非常多。如果大家手邊有高中/大學資訊社團、開源專案，或是也在籌辦類似的學生競賽，真的非常推薦去申請他們的社群贊助計畫，絕對是學生團隊的超級大乾爹！

![國雲網路 NCSE Network 社群贊助計畫官網首頁](../../assets/posts/thjcc-ctf-summer-2026/ncse-network-sponsor.png)

#### 2. 算牌時間：如何優雅地向贊助商請求資源？
雖然有贊助商罩著，但總不能兩手一攤跟乾爹說「隨便給我頂配、越多越好」吧 ww。身為網管組長，賽前最重要的一道數學題就是「資源估算」。你必須根據預期規模算出一份合理的硬體清單，我們大致上是用下面這套邏輯在抓資源的：

$$ \text{所需總資源} = (\text{預估隊伍數} \times \text{併發係數}) + \sum (\text{各類題目數} \times \text{題目預估最大資源}) + \text{安全留裕度 Buffer (20\%~30\%)} $$

講白話一點就是：
- **平台基本盤**：預估這次會有多少隊伍參賽？開賽瞬間會有多少人狂敲首頁？這決定了 CTFd 平台的 CPU 核心與記憶體基本盤。
- **題目硬體開銷**：出題組這次到底丟了多少題？哪些是吃記憶體怪獸的 Web 服務？哪些是動態開容器的 Pwn 題？每題都要預先估算一個記憶體與 CPU 上限。
- **防止翻車的 Buffer**：工程師的鐵則就是「絕對不要把資源抓到剛好 100%」。多抓個 20% 到 30% 的緩衝空間，才能應付開賽時各種突如其來的流量與突發狀況。

**但現實往往比想像更骨感——賽前題目根本還沒出完啊！**  
相信辦過 CTF 的人都懂，出題組在死線前幾天極限輸出是常態中的常態。在我們必須向贊助商提出申請的那個時間點，題目清單往往只填了一半，題型比例（到底有幾題吃資源的 Web/Pwn、幾題純靜態的 Misc/Crypto）完全是個謎。

這時候就非常考驗網管的「玄學經驗」了。我們必須參考過去幾屆的參賽人數與出題規模，用過往的經驗去推敲出一個合理的範圍區間（Range Estimation）來做預估。

更棒的是，**國雲網路的社群贊助計畫非常有彈性，並不要求你在第一時間就把資源規格完全寫死！**  
這對網管來說簡直是救命稻草。我們的應對策略是：**一開始申請時先抓得保守一點**，先確保基本盤平台與核心靶機能穩穩跑起來；等接近開賽、出題組陸續把題目交齊之後，如果發現某些題目特別吃資源或記憶體吃緊，再即時向國雲網路提出**追加配額與彈性擴額**。這樣不僅不會浪費贊助商的資源，也大大減輕了網管賽前瞎猜規格的心理壓力。

#### 3. 架構大忌：為什麼打死都不能只用一台主機？（CTFd 與靶機的分家哲學）
在開會討論架構時，可能偶爾會有人冒出一句：「欸，一台頂配機器把 CTFd 跟 Docker 題目全塞進去不就好了？集中管理不是超省事嗎？」

聽到這種想法，我只能說：**先不要，真的會出大事！**

我們這次堅持把架構嚴格拆成「CTFd 平台主機」與「題目靶機主機」兩台獨立伺服器，背後主要有兩大血淚考量：

1. **爆破隔離與防打爆（資源防護）**：  
   大家都很清楚 CTF 選手有多殘暴，解題時狂寫 Python 腳本多線程爆破、發送各種惡意 Payload、搞出無窮迴圈都是家常便飯。如果把靶機跟 CTFd 塞在同一個鍋子裡，只要某道題目被選手玩到 OOM（記憶體溢出）或 CPU 飆上 100%，整台伺服器一卡死，CTFd 平台就會直接噴出 `502 Bad Gateway`。這時候全場所有人都沒辦法交 Flag，Discord 頻道大概五秒內就會被「平台倒啦！」的哀嚎淹沒，那種場面光用想的就胃痛。
   
2. **資安風險與內網隔離（權限防護）**：  
   題目靶機上本來就充滿了各種故意設計的洞，甚至很多題目本身就是以 RCE（遠端代碼執行）為目標。要是兩者共用同一台機器，萬一某個題目容器被選手徹底打穿甚至提權成功，攻擊者順著 Docker 內網一摸，直接把隔壁 CTFd 的資料庫跟所有題目的 Flag 一鍋端走，那這場比賽就可以直接提早宣布全體下課了。

所以說，把計分板與靶機物理/虛擬隔離分開，就是網管能睡個好覺的第一道保險。

![THJCC CTF 雙主機架構與網路隔離示意圖](../../assets/posts/thjcc-ctf-summer-2026/ctf-network-architecture.svg)

#### 4. 做出自己的特色：CTFd 專屬主題與視覺設計
雖然幾乎所有的 CTF 競賽底層都是跑 CTFd 這套開源平台，但老實說，如果每場比賽打開來都長得千篇一律，總覺得少了一點靈魂。

每一場比賽都有屬於自己的主視覺與調性，為了讓參賽選手從登入那一刻起就有沉浸感，我們在賽前花了不少心思針對 CTFd 進行客製化主題（Custom Theme）開發。從大會專屬的深色現代感配色、首頁賽事規章與獎金卡片展示，到挑戰看板（Challenge Board）的分類篩選與題目卡片排版，讓整場比賽不僅穩固，在視覺體驗上也充滿了屬於 THJCC 的獨特科技感！

#### 5. 設定 CTFd 時那些容易踩雷的小眉角
把主機開好之後，接下來就是部署 CTFd 了。雖然官方有現成的 Docker Compose 可以一鍵拉起，但在實際生產環境給幾百人打的時候，還是有幾處容易翻車的細節要特別處理：

- **Nginx 反向代理與 Rate Limiting（限流保護）**：  
  這是重中之重！如果沒在 Nginx 設定限流規則，開賽前五分鐘你就會看到 Nginx log 像瀑布一樣狂刷，伺服器分分鐘被選手的自動化掃描腳本灌到中風。一定要針對登入、提交 Flag 的 API 端點設定適當的請求速率限制。
- **Redis 快取與 Session 管理**：  
  強烈建議一定要掛上 Redis。開賽那一瞬間，大家都在瘋狂按 F5 刷新題目清單，如果每次請求都直接去敲 MySQL 資料庫，資料庫連接池瞬間就會被塞滿。有 Redis 幫忙扛住熱門資料快取與 Session，整體反應速度會順暢非常多。
- **Cloudflare CDN 防護**：  
  在最外層套上 Cloudflare，除了可以幫忙吃掉絕大部分靜態資源（CSS、JS、圖片）的流量，還能擋掉一些基礎的奇怪掃描與小規模流量衝擊。
- **動態題目的容器生命週期管理**：  
  如果這次有出「一隊一實體」的動態題目，務必確認自動超時回收機制（Auto Clean-up）有正常運作。不然測試時開一堆容器沒關，正式開賽前就會發現硬碟跟記憶體早就被一堆死掉的幽靈容器吃光了，連開新題目的空間都沒有。

### 賽中問題處理與救火現場

開賽哨聲一響，網管組的「胃痛時刻」就正式開始了。就算賽前測得再怎麼完美，開賽後永遠會有各種超乎想像的突發狀況等著你。

#### 1. 監控神器登場：血壓飆高的 `btop` 實錄
在整個比賽過程中，網管終端機裡幾乎常駐開著的工具就是 `btop`（btop++）。這款基於 C++ 的終端資源監控工具不僅畫面好看，各項指標更新也非常即時，是隨時掌握主機健康度的絕對神器。

只不過，當你看到下面這個畫面的時候，你的心跳大概也會跟著 CPU 一起飆破天際：

![btop 監控畫面：CPU 8 核心全滿載與驚人的 Load Average](../../assets/posts/thjcc-ctf-summer-2026/btop-cpu-100-overload.png)

沒錯，這就是我們在賽中真實捕捉到的「災難現場」——**整整 8 顆 CPU 核心全部被灌到 100% 滿載，紅通通一片，Load Average 甚至直接飆到了驚人的 `166`！** 行程清單裡塞滿了一整排 Crypto 題目的 Python 與 Gunicorn 運算行程。看到這個數字的當下，手心真的會不自覺冒汗。

#### 2. 救火現場（一）：題目本身程式碼「漏水」，資源被瘋狂佔用
為什麼 CPU 會突然飆成這樣？追查之後才發現，這往往是出題時的程式邏輯寫得不夠嚴謹。

有些題目（特別是需要複雜數學運算或多行程處理的題目），在選手建立連線或發送 Payload 後，背景沒有設計完善的連線超時與 Process 釋放機制。結果只要幾百個選手同時連進來狂轟，後端就會不斷 Fork 出新的 Python process 卻沒有正常回收，短短幾分鐘內就把整台機器的運算資源給徹底榨乾了。這時候網管就得一邊緊急連進主機手動 `kill` 掉死鎖行程，一邊跟出題組協調調整題目的服務配置。

#### 3. 救火現場（二）：賽前驗題缺漏與 Port 映射靈異事件
另一個讓人手忙腳亂的狀況是「賽前驗題的疏漏」。

由於出題時間緊迫，有少數幾道題目在賽前驗題時可能只測了本地連通性，卻沒發現對外 Port 映射配置有誤，或是容器啟動腳本權限不足導致開賽後根本沒正常 Listen。

開賽不到十分鐘，Discord 的 Ticket 系統就陸續有人開單回報連不上題目。這時候只能摸摸鼻子趕緊登進靶機翻 log，看看到底是哪道題目的 port 映射手殘寫錯或容器沒跑起來，趕快修好重啟，再默默把 Ticket 關掉回覆「已修復～」ww。

#### 4. 救火現場（三）：題目被非預期打到下線與反查 IP 封鎖
在 CTF 賽場上，選手的思路永遠比你想的還要奔放。有時候某些題目會被選手的非預期 Payload 直接打出崩潰（Crash），甚至整道題目的 Docker 容器直接罷工下線。

遇到這種情況，網管的工作可不只是手動把容器重啟這麼簡單。我們必須立刻調閱 Nginx Access Log 與容器日誌，分析到底是被正常解題打爆，還是有選手在使用過於激進且無延遲的自動化腳本進行暴力掃描：

1. **分析日誌與行為模式**：過濾出異常發送大量請求的請求特徵與攻擊路徑。
2. **反查來源 IP**：確認惡意連線的來源 IP 網段。
3. **即時動態封鎖**：立刻在 Linux 本地的 IPTables 下達封鎖規則（IP Drop / Rate Limiting），先將惡意流量擋在門外，確保其他守規矩的選手不會受到波及。

### 賽後資料導出與總結

當比賽結束的倒數歸零那一刻，全場選手或許能鬆一口氣去補眠，但對網管組來說，最後一哩路的收尾工作才正要展開。

#### 1. 賽後資料導出與 CTFtime 成績匯出
因為 THJCC 這次有在國際知名的 **CTFtime** 賽事平台上正式登錄，這代表我們賽後必須產出符合規範的官方成績資料，提交給 CTFtime 官方進行權重計算與全球戰隊積分同步。

網管組在賽後主要要處理以下幾份關鍵資料的導出：
- **CTFtime 分數榜 Feed**：透過 CTFd 匯出符合 CTFtime 格式的分數榜（Scoreboard JSON），包含各隊伍名稱、解題時間戳、最終得分與排名，讓官方能夠準確無誤地更新積分。
- **完整提交日誌 (Submission Logs)**：匯出所有隊伍提交 Flag 的詳細紀錄（包含正確與錯誤的嘗試、提交時間與來源 IP），提供給出題組與審核組核對 Writeup，並檢查是否有抄襲、Flag 共享或異常代刷等違規行為。
- **資料庫與題目環境留存**：將整場比賽的 CTFd 資料庫與各題目設定做完整備份，作為未來賽事復盤與社團傳承的寶貴資料庫。

#### 2. 網管組長心得與總結
從第三屆那個連發生了什麼事都不知道、懵懵懂懂「水過去」的菜鳥組員，到這次 2026 THJCC 夏季賽親自接下網管組組長，這段旅程對我來說是一次極具價值的實戰歷練。

老實說，身為網管組長，你的戰場不在解題排行榜上，而是在那些看不到的終端機視窗、Nginx Log 與 `btop` 的即時指標裡。看著 8 顆 CPU 飆到 100%、Load Average 衝上 166 的心驚膽跳，在 Discord 冒冷汗搶修 Port 映射的緊張感，以及最後看到平台頂住全場流量順利完賽的釋懷——這些幕後的酸甜苦辣，是單純當參賽者時完全無法體會到的。

一場成功的 CTF 比賽，除了參賽選手的神仙打架與出題組的精心設計，幕後能有一套穩如泰山的基礎設施更是不可或缺的基石。

最後，特別感謝總召的信任與各組夥伴的互相配合，更要再次感謝 **國雲網路 (NCSE Network)** 在賽前與賽中提供的高品質 VPS 主機與網路資源支援，讓這次 2026 THJCC 夏季賽能夠圓滿落幕！
